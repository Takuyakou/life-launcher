# Phase 6.1 — 追加仕様と維持する契約

この文書は追加改善の目標仕様。現物との照合前に「実装済み」と扱わない。
旧Phase 6の完了機能は維持する。特に完成したMainの密度・色・並びを再設計しない。

## 1. ユーザーに見せる単純な流れ

```text
次の一手 ─────┬─ 今日へ ──────────┐
やりたいこと ─┤                          ↓
              └─ 既存候補として表示 → 今日を組み立てる → 今日へ → 今日の3件
                                                                    ↓
                                                              タイマーで開始
```

Builderへ「登録してから」Today3へ進む必要はない。
Builderは同じ元データを見る別の窓で、独立した登録段階ではない。
`今やる一手`は迷った場合の推薦・開始入口として現行のまま残す。
Today3を必ず通らないとDo Nowを使えない構造にしない。
`今日の勝利条件`はその日の判断基準。Builderからの送付先にも候補sourceにもしない。

## 2. 操作マトリクス

| 場所 | 新規作成 | 表示する主操作 | この工程での注意 |
|---|---|---|---|
| 次の一手 | ＋追加（既存Project詳細登録） | 今日へ、右クリック編集 | Projectの能力を削らない |
| やりたいこと | ＋追加（新しい小型modal） | 今日へ、既存context menu | 一言の登録を軽く保つ |
| 今日を組み立てる | なし | 今日へ、ページ移動、開閉 | 勝利条件等への送付先select・削除/dismissなし |
| 今日の3件 | なし | 短時間/通常開始、満了後の終了確定、条件付き次の3件 | 既存の完了・source関連付けを維持 |
| 今やる一手 | なし | 短時間/通常開始、別の候補 | 推薦アルゴリズムを変更しない |
| 今日の実行 | なし | 記録の表示・開閉 | 実行履歴を残す |
| 今日の勝利条件 | 既存の設定/編集を維持 | 既存の操作 | Builder整理を口実に勝利条件を消さない |

※既存Today3の取り外し/編集等、今回の話題外の操作を勝手に削らない。
その意味・completionへの影響は基準テストで保護する。

## 3. Mainの見た目と順序

```text
今日の勝利条件
今やる一手
今日の3件
今日を組み立てる
次の一手
やりたいこと
今日の実行
```

補助headerの文法:

```text
⌄ 今日を組み立てる  12件  次の一手・やりたいことから、今日やるものを選ぶ
⌄ 次の一手  ＋追加  5件  各プロジェクトで、次にやること
⌄ やりたいこと  ＋追加  7件  あとでやりたいことを置いておく
⌄ 今日の実行  3件  タイマーで実行した内容
```

件数はタイトル付近。追加がないsectionで見えないダミーbutton用の空白を残さない。
長い補足は狭幅で折り返し/省略してよいが、タイトル・主要actionを押しつぶさない。
Today3は別の実行カード体系のまま。全体の枠、font、paletteの入替えは禁止。

## 4. Builderの候補生成

### 4.1 元データ

P61-00の承認後、Projectの設定済みnextStepとWishlistを候補源とする。
Project自体の削除/アーカイブ等の有効性判定は既存実装に従う。
空のnextStepを`次の一手を書く`という実行対象として生成しない。
Wishlistの空/無効な値も候補化しない。表示上のtrimは元データの勝手な書換えにしない。

同名の項目でもIDが別なら別候補。同じsourceが2経路に出てもduplicateを作らない。
sourceを識別する安定IDは既存のstable source identityを再利用する。
行番号・ページ番号・labelのみをキーにしない。

### 4.2 元データ以外を作らない

新しいBuilder用入力schema、保存配列、手動のstaging listは作らない。
元データを変更すれば候補表示へ反映されるが、ページ操作や開閉では保存しない。
Session由来の候補を外しても、sessions.jsonl、今日の実行、記録検索、
他のnextStep候補補助まで削除/無効化しない。
過去のSession由来Today3項目があれば互換表示・完了・保存を維持する。

### 4.3 一覧とページング

既存の5件/pageを継続。8件を含む固定打切りを復活させない。
順序は現行の安定したsource順を基本とし、ランダム化や独自scoreを追加しない。
NextStep/Wishlistの出所は短いラベルで分かるようにする。大きい分類カードは増やさない。

各行の主操作は`今日へ`。プルダウンで送付先を選ばせない。
新たな複数選択checkbox、選択用一時リスト、一括確定dialogは今回作らない。
既に選択済みは、元IDで判定して`今日に選択済み`等を表示する。
完了の✓とは混同させない。disabledの場合も理由が分かること。

件数とpage表示は同じ候補配列から計算する。
元項目削除・候補source絞り込み・再読込で総ページ数が減ったらpage clamp。
0件ではpaginationを出さない。候補が見えなくなった際もfocusを失わない。
既存のpage状態保存方針は、変更不要なら維持する。

## 5. Builderの削除/dismiss廃止と互換性

報告書の「削除」は元sourceを消さないdismissだった。今回そのUIと書込経路を撤去する。
単にmenuだけ消し、過去のdismissを今後も適用して候補を隠し続けてはいけない。

第一案:
- 新しいBuilderでは旧dismissを候補filterへ適用しない。
- 旧値は読み込み互換のため保持し、起動時にconfig全体を書き換えない。
- 新しいdismiss値は生成しない。
- 元Project/Wishlist/Session/Today3は消さない。
- 従来隠した候補が再表示されることは、今回の意図した変更としてGuide/報告に短く記す。

実装上、型やvalidation変更が必要なら影響を監査する。
破壊的なkey削除・全configリセットで解決しない。戻しが可能な最小変更に留める。
Builder右クリックから編集/削除を新規追加しない。既存の元項目案内があれば移動だけは可。

## 6. Today3の入力口整理と「今日へ」

Today3から新規項目を作るheader/body/empty-state/context-menu等の入口を除く。
削除対象は**登録用の＋追加/自由入力**。実行button、次batch、既存履歴は対象外。
NextStep/Wishlist/Builderの`今日へ`は共通の既存採用処理へ接続する。
新しい「今日の候補へ追加」ボタンは作らない。

採用時:
1. 対象sourceが現在も有効か確認。
2. 現行batchの3件上限とstable identityのduplicate条件を検査。
3. 元データを消さずToday3へ採用。
4. 保存失敗は成功表示せず、基準のrollbackを維持。

二重クリック・同じ候補をsource側/Builder側から続けて押す操作をテストする。
満枠時は`いま選べるのは3件までです。`等、1日3件しかできないと誤解させない表現にする。
新しい無制限枠・自動batch繰越・自動補充を追加しない。

**snapshotとidentityを混同しない。**
Today3へ採用済みの文章・起動action・分数を元項目編集のたびに勝手に書き換えない。
採用後のsource更新/削除、Timer開始後の編集は既存contractに合わせて保護する。
「次の一手と同じ名前だから完了」のような曖昧な対応づけは禁止。

## 7. Today3が空のとき／次batch

### 候補があるがToday3が空

```text
今日の3件  0件
まだ決まっていません。候補から今日やるものを選べます。
今日の候補を見る
```

最後の操作はBuilderを展開して見出しへ移動/focusするナビゲーション。
新規登録modalを開かない。タイマーも自動開始しない。

### 候補自体が0

Today3/Builderの空状態から、`やりたいことへ` / `次の一手へ`のように
既存の登録元へ案内する。下のsectionを開いて、既存＋追加へfocusしてよい。
フォームはユーザーがその＋追加を押してから開く。
空欄で黙る、長い教程を強制する、同じ入力フォームを上段に増設する、のいずれもしない。

### 次の3件

現行の「3件が完了し、次batchへ進める」という判定と明示操作は維持。
押したあとの案内先をBuilderへ接続し、削除済みToday3追加modalへ飛ばないようにする。
履歴を残す現行処理、1〜3件で開始可能な枠、3件完了時だけのCTAは変えない。
候補を選ばず閉じても勝手に3件を補充しない。

## 8. Today3 / Timer — 今回変更しない意味

報告書の完了は**Timer満了後の終了確定**。
予定時間0到達、dialog表示、手動停止、別Timerへの切替だけで完了にしない。
継続を選ぶ経路がある場合は現行どおり。Guide文言も実際のbutton名に合わせる。

1分未満停止・一時停止除外等の細部は現物のテストに従う。
Do Now/Today3の開始元が違っても、現行のidentity連携を壊さない。
継続時/失敗時のSession重複を作らず、実行履歴を消さない。

## 9. Wishlist登録を小さいモーダルへ

既存の行内入力を撤去し、NextStep詳細dialogと**操作文法**を揃える。
同じフォーム内容にしない。

```text
やりたいことを追加
あとでやりたいことを、ひとまず残しておきます。

やりたいこと
[ 気になっていた本を読む ]

[ キャンセル ]   [ 保存 ]
```

- 入力は既存Wishlistの本文1項目を基本とし、現行schema/ID/validatorを再利用。
- Project、北極星、今週の重点、起動action、手順書、分数は要求しない。
- メモなど新しい永続fieldを今回のために増やさない。
- 入力開始focus、footer配置、button階層、余白、Escape、validation、失敗表示を共通化。
- 次の一手の巨大なProjectフォームの高さや空欄まで模倣しない。内容に合う小さいdialog。
- 保存中は二重submitを防ぐ。成功時だけ閉じ、失敗時は入力を残す。
- cancelでは何も保存しない。閉じたら元の＋追加へfocusを戻す。
- 日本語変換中のEnterを送信に使わない。composition/既存IME規約を守る。
- backdrop/Escapeの未保存入力扱いは既存modal conventionを監査して統一。
- dialogをbuttonへnestedにせず、role/title/focus管理を既存の良い実装に揃える。

Wishlistの既存context-menu編集/削除/今日への意味は維持。
共有フォームへ寄せる場合も「追加」と「編集」を混同して新規IDへ置き換えない。

## 10. NextStep登録の意味を明確にする

画面の`Project / 次の一手を追加`と、名前・北極星・重点・手順書等の詳細項目には
作成対象の分かりにくさがある。P61-00で実際のhandlerを確かめる。

- Projectを新規作成するなら、dialog titleを`プロジェクトを追加`等にする。
  補足は`取り組みと、次にやることを登録します。`など。
  名前fieldは`プロジェクト名`にし、次の一手fieldとの違いを示す。
- 既存ProjectのnextStep設定なら、`次の一手を設定`等にし、Projectの新規作成と混同しない。
- 上部のNextStep sectionと＋追加は残す。既存の詳細設定能力を削らない。
- 名前の整合を直すだけのために、新しいProject管理画面やデータモデルを作らない。
- Source未設定時にDo Nowへ表示されない条件等はGuideで実装準拠に説明する。

## 11. Guide・空状態・短い文言

Guideの専用計画はGUIDE-UPDATE.md。
操作ラベルは`今日へ`などの画面の日本語に揃え、ユーザー向けには
source identity / derived view / batch / 昇格 / staging areaを使わない。
`作成 → 選択 → 実行`は理解補助であり、毎回すべてのsectionを通る手順にしない。

## 12. 不確定点の扱い

Do Nowの推薦変更、dayStartHour変更、現在のToday3 snapshot連動変更、
失敗時の新しい保存方式、Sourceへの新field追加はこの仕様から自動的に導かない。
必要性が判明した場合、影響と最小案をP61-00または該当Stageで報告して止める。
