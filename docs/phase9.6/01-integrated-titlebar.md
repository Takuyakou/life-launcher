# P96-01 — 一体型タイトルバー(メイン画面・手順書ビューアー) 報告

- 日付: 2026-11-05
- ブランチ: `feature/p96-01-integrated-titlebar`
- 最終ステータス: **DONE**(実装・テスト・ゲート完了。実機確認のうち人の手が必要な項目は「オーナー確認待ち」)

## 実装内容の要約

メイン画面と手順書ビューアーからWindows標準のタイトルバーを外し、窓の右上(右端から 8px)に固定する窓のボタン3つと、ドラッグできる範囲(上部メニュー行・上端の余白・ブランド表示・ダイアログの幕の上端の帯)を一体化ヘッダーとして実装した。window-stateプラグインが `decorated` を保存・復元しないようにし、幅の予算はオーナー決定の案A(行内gap 8px＋大・特大で ≤1150px のラベル隠し拡大＋行の右余白の動的予約)で 24通りすべて収まることを実測で確かめた。

## 判断メモ

- 窓のボタンは行内ではなく fixed 配置(オーナー指示1)。行は重なる幅のときだけ `padding-right`(最大111px)で空きを取る。topBar の box は動かないため phase89 の幅テストは無変更
- 実装中に見つけた構造上の問題と対応: (1) `.topBar` はグリッドアイテムで `min-width: auto` のため、縮められない子を含むと指定幅を無視して膨らみ窓の外に出る → `min-width: 0` を追加。(2) 拡大タイマー表示中に `.mainPanel` 全体へ `inert` が付き、ヘッダー内の窓のボタンまで押せなくなっていた → inert の対象を本文領域に変更(P8.10 のフォーカストラップと Tab の契約は無変更で通ることを phase810 全7テストで確認)
- ダイアログ右上の × の帯回避は、オーナーの「今日やるものを選ぶ」の決定を同じ形(右上の ×)を持つダイアログすべてに適用した。`calc(50% − 50vw + 143px)` はダイアログの幅や padding によらず正しく帯の左端+8px に置く式
- 実装前の BLOCKED 報告(本PRの最初のコミット)は、測定の段階での報告。案A決定後に実装を再開した

# 追加の修正(2026-11-05 オーナー決定)

PR #141 に追加した4点。マージはしない(オーナー確認後に判断)。

## 1. メインウィンドウの初期幅を 1080 → 1200

- `src-tauri/tauri.conf.json` の main 窓 `width` を `1200` にした。高さ 680・最小幅 860 は変えない。
- 窓の状態の保存・復元は今までどおり(保存済みの幅があればそれが優先される)。`src-tauri/src/lib.rs` のテストデータ `V141_STATE_JSON`(`"width": 1080`)は v1.4.1 の保存状態の写しなので変更しない。

## 2. 上部メニューの文字を「実測」で隠す

決まった幅の境目(`@media` の ≤1050 / ≤900、P96で足した ≤1150)をやめ、文字を出したときに必要な幅を測って、行に入りきらないときだけ隠すようにした。表示サイズ(標準・大・特大)とメイン/記録のどれでも同じ決め方。

- 新しい `src/topMenuLabels.ts`: `pickTopMenuLabelLevel(neededWidths, availableWidth, currentLevel)` が段階を決める純粋関数。`useTopMenuLabelLevel(measureKey)` が実測と再測定を受け持つ。
- 段階: `0`=6つとも出す / `1`=自動起動・ミニ・使い方・設定の文字を隠す / `2`=記録・手順書も隠す。隠したボタンは `title` と `aria-label` を保つ(テストで担保)。
- 隠す境目と戻す境目は 8px 離す(`TOP_MENU_LABEL_HYSTERESIS_PX`)。隠すのは入らないとき、戻すのは 8px の余裕があるときだけ。
- 再測定のきっかけ: `ResizeObserver`(行と見出し)、`window resize`、`document.fonts.ready`、表示サイズの切替。幅が変わったその場で測り直すので、文字が出たままのフレームはない。
- 幅 760px 以下は今までどおり縦積みで、文字は出さない(JS も同じ幅で段階2にする)。

### 実測した段階(コミットしたテストの期待値)

必要な幅(見出し＋すきま8px＋メニュー)/ 使える幅(行の幅−右の空き)。段階はメイン画面の見出しで決めるため、**メイン画面と記録画面で同じ値**になる。

| 幅 | 使える幅 | メイン 標準/大/特大 | 記録 標準/大/特大 |
| --- | --- | --- | --- |
| 860 | 457 | 2 / 2 / 2 | 2 / 2 / 2 |
| 1080 | 677 | 0 / 1 / 1 | 0 / 1 / 1 |
| 1200 | 797 | 0 / 0 / 0 | 0 / 0 / 0 |
| 1440 | 1037 | 0 / 0 / 0 | 0 / 0 / 0 |
| 1920 | 1180〜1400 | 0 / 0 / 0 | 0 / 0 / 0 |

- **1200px では標準・大・特大のすべてで6つの文字が出る**(オーナー指定の確認項目)。必要幅は 653 / 685 / 753、使える幅 797。
- 860px は6つとも隠れる(今までは記録画面だけ「記録」「手順書」が残っていたが、画面で差が出ないようにそろえた)。
- 30通り(5幅 × 3表示サイズ × メイン/記録)すべてで、文字はボタンからはみ出さず、重なり・折返し・行のはみ出しなし。窓のボタン3つは常に全部見える。
- メイン画面と記録画面を切り替えても段階が変わらないことを、5幅 × 3表示サイズで確かめるテストを足した。

### 判断メモ(実測の作り方)

- 実物の幅をそのまま読むと「狭いので縮む → 縮んだ幅で測る → 入ると判断する → さらに縮む」の循環になる。**複製を max-content で測る**方式にした。
- 複製は `.topBar` の外(同じ `.mainPanel` の中)に置く。`.topBar[data-top-menu-labels="2"]` の隠す決まりを複製が受け継ぐと、常に「隠した幅」を測ってしまい段階が 0 に戻る(実装中に踏んだ)。`.mainPanel` の中なら表示サイズの文字の大きさはそのまま効く。
- 見出しの幅も複製で測る。実物は狭いと縮み、`scrollWidth` でも本当の幅は取れない(省略表示のため)。
- 見出しの複製は、**記録画面でもメイン画面の見出し(「今日 N分」＋日付)を組み立てて測る**(オーナー決定 2026-11-06)。記録画面の見出し「記録」を測ると画面ごとに段階が変わるため。
- 表示切替のボタンだけは画面で文字が変わる(記録/メイン)ので、複製の文字を**2つの画面で長い方**に置き換えて測る(2.4px の差が境目で段階を変えないように)。このため切り替えてもメニューの幅も位置も変わらない。
- 段階を決めるフックは、`config` が無いときに早期 return する場所より前で呼ぶ必要がある(後ろに置くとフックの数が変わって画面が落ちる)。見出しの文字は `config` の読み込み後に `measureKey` の変化で測り直す。


## 3. 窓のボタンの乗せた色・押した色

- 乗せたとき/キーボードで移ったとき: 背景 `--line`、アイコン `--text`(今までの `--menu-hover-bg` から変更)。
- 押したとき: 背景 `--line-soft`(今までの `--menu-active-bg` から変更)。閉じるの乗せた色(`--error`)より優先する点は今までどおり。
- 閉じるに乗せたときの `--error` は変更なし。メイン画面と手順書ビューアーの両方に効く(同じ部品)。
- `docs/spec/current-spec.md` §6.1 の窓のボタンの表を更新した。

## 4. 窓を戻した直後に乗せた色が残る問題

- 最小化・タスクトレイから戻したとき、直前にマウスを乗せていたボタンの色が残っていた(実機確認でオーナーが発見)。
- 窓のフォーカスが戻った時点(`onFocusChanged` が true)で乗せた色を抑止し、次にマウスが動く(または押す)まで戻さない。`.windowControls--hover-suppressed` を付ける方式。キーボードの輪と押した状態は抑止しない。
- メイン画面と手順書ビューアーの両方。テストで「乗せる → フォーカスが戻る → 透明 → 1px 動かす → 色が戻る」を確かめた(閉じるの赤も同じ)。

# 追加の修正2(2026-11-06 実機で見つかった不具合)

オーナーが実機(1200px・表示サイズ「大」)で確認したところ、窓の右端をドラッグして狭めても**文字を隠す段階が一度も変わらなかった**(約1070px で文字が残ったまま見出しが2行に折り返し、約930px で文字とアイコンが詰まる。最小化から戻しても同じ)。自動テストは緑だったため、テストの穴も含めて直した。

## 原因(実機で確認した)

- 不具合の状態では `data-top-menu-labels` が `0` のまま。Chrome DevTools Protocol で実アプリにつなぎ、**測定用の複製が DOM に追加された回数**を数えると、窓を 1200→1070→930 と変えても **0 回**だった(= 測定が一度も走っていない)。
- 同じ状態で**表示サイズを「大」→「特大」に切り替えた瞬間**に段階が `2` になり、**その後のリサイズには追従した**。つまり「幅の変化を購読する effect が、行の要素が無い時点で一度だけ走り、以後 `measureKey` が変わるまで再実行されていなかった」。
- `useTopMenuLabelLevel` は行・メニューの要素を `useRef` で受け取り、effect の依存を `[measure, measureKey]` にしていた。effect が「要素がまだ無い」タイミングで走ると `bar` が null のまま早期 return し、**要素ができても購読(`ResizeObserver` / `window resize`)が付かない**。
- 自動テストが再現しなかった理由: テストは「幅を決めてから読み込む」順で、要素がそろった後に effect が走っていた。実機は「読み込んでから幅を変える」順で、要素の登場と effect の順序が逆になっていた。

## 修正

- 要素を **コールバック ref(state)** で受け取る形に変えた。要素が DOM に付いた時点で state が変わり、effect が作り直されて購読が付く。画面の入れ替えで要素が差し替わったときも同じ経路で付き直す。
- 購読は行の要素(`ResizeObserver`)・`window resize`・`document.fonts.ready`・`measureKey`(表示サイズ)・見出しの文字(分数)。幅が変わったその場で測り直す(次のフレームまで文字が残らない)。

- メイン画面と記録画面を切り替えても段階は同じ(1070px で両方 `1`・2文字)。
- 表示サイズを切り替えた直後も測り直される(「大」→「特大」で即座に段階が変わった)。
- 不具合時は 1070px で見出しが2行(高さ 53px)に折り返していたが、修正後は全幅で1行(26px)。
